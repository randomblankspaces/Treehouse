# Build Design Decisions (formerly Open Build Questions)

> **For agents — what this file is:** Design questions for the build. **Status: decided (SCOPE D25).** Every *recommended default* below is now the decision, with one change: **OQ12's output metric is deterministic, with no LLM judge.** OQ13 doesn't apply (solo build), and OQ14 was open until round 6 (now superseded by D67). Build on these. Change one only by logging a new decision in SCOPE.md. **Round 6 (2026-11-04):** the two adopted designs changed several rows. Each changed row ends with **Superseded by Dxx** and a one-line note; where a superseded note and the original text differ, the note wins. Details are in [design/SYSTEM-DESIGN.md](design/SYSTEM-DESIGN.md) and [design/IMPLEMENTATION-DESIGN.md](design/IMPLEMENTATION-DESIGN.md).

| # | Question | Decision (accepted default, D25) |
|---|---|---|
| OQ1 | **What a synthetic task contains and what "good workflow" is measured against.** We get no ADB inputs (D13), and an ADB rubric is unconfirmed. | Each synthetic task ships an **expected-workflow spec** listing required and forbidden tools, ordering rules (e.g. "search before fetch"), a step limit, and a "done" condition. A deterministic evaluator checks the trace against it. An optional LLM evaluator rates planning and recovery against a written process rubric, and doubles as the second swappable evaluator (D2). **Superseded by D52, D62:** a task is now a task card (AOI, keying per step, forbidden sources, `must_notice`, sampling and gold plans). The optional LLM process evaluator is replaced by deterministic Panels 1–2; an optional trajectory judge may appear only as a labelled column outside Panel 1 (SD A6) |
| OQ2 | **Which statistics** (D1) | For each configuration: N trials per task (set per eval, default 5). Success rate with a 95% Wilson confidence interval. Mean and spread of steps, latency, cost, errors, and the output metric, with bootstrap 95% CIs. A vs B: permutation test with p-value and effect size. numpy/scipy only. The report states plainly when CIs are wide because N is small. **Superseded by D68:** paired cluster or paired bootstrap CIs (Wilson only for simple proportions), a fixed two-stage trial plan (K=3 first), permutation tests with Holm over a committed primary list, at least 5 per arm, minimum detectable difference reported; every MVP comparison labelled exploratory |
| OQ3 | **Proving the evaluator works** | An evaluator check: plant known-bad traces (failed tools, loops, wrong order) and known-good ones, then report the detection rate. For the LLM evaluator, re-score the same trace k times and report agreement. **Superseded by D48, D53:** the evaluator check is the planted-policy integration tests (fabricator, skimmer, key-peeker, looper, overconfident, budget-stop; ID §6 I1–I7) plus seeded method tests M1–M17 for the trust engine. The verifier's own accuracy comes from keyed controls in the same batch |
| OQ4 | **How comparisons are designed** (D3) | One baseline plus variants that each change one thing. **Models:** 2 Bedrock models. **Harnesses:** Strands vs. a plain Bedrock Converse tool loop. **Tool sets:** RODA only vs. RODA + 1–2 shortlist servers + LGND embeddings tool. That's 4 configurations; with 5 tasks × 5 trials, about 100 runs, likely under about $30 (confirm on Day 1 from real per-run cost). **Superseded by D60, D68:** one factor at a time: model (cross-family), harness (plain loop vs Strands, only if both exist), tooling (with/without `clay_search`), verifier (same vs cross-family). The run-count and dollar figures are replaced by measuring one real vision run first (D65) |
| OQ5 | **Hot-swap evaluator = re-score old runs** | Yes: swapping the evaluator re-scores stored traces without re-running the agent. This is the same code path as replay |
| OQ6 | **What "context given" (D9) records** | Run manifest holds: prompt, system prompt, tool list with exact schemas, MCP server names and versions, model ID and parameters, harness name and version, budget-guard settings, evaluator version, task-spec version, seed |
| OQ7 | **Budget-guard limits** (D6) | Four optional limits: max steps, max tokens, max $, max wall-clock seconds. Hitting one stops the run and logs `budget_exceeded`. The run **counts as a failure** in the stats, not as dropped. **Extended by ID §2–§3 (F11):** the guard also limits tool calls and bytes, with events at 50/80/100 %. **Separately, D65:** a cross-run spend ledger caps total spend ($250/$350/$450) |
| OQ8 | **Which errors count against the agent** (D12) | All errors are logged and tagged by source. **agent** (bad args, nonexistent tool, loop, giving up) and **tool** (MCP failure or timeout) count against the agent. **infra** (Bedrock throttling, network) is reported but excluded from the agent's score. **Extended by D51:** error sources are agent, tool, policy (forbidden source, `as_of`), budget and infra. A forbidden-source attempt is a logged agent error (`key_access_attempt`) |
| OQ9 | **Which AWS services** (D10) | Bedrock for the agent and LLM evaluator. S3 as an optional run store (local folder by default). CloudWatch/X-Ray as the second tracer. A small CDK stack for the bucket and IAM role (infrastructure as code). Batch trials on Lambda/ECS is a stretch goal. **Superseded by D67:** a capability probe (K1) decides; guaranteed floor is Bedrock Converse plus a versioned S3 run store; Object Lock, key-bucket IAM Deny and CDK for what we deploy are Must-1; CloudWatch, Lambda and invocation logging are Should; batch trials stay a stretch; every seam has a local stand-in and the manifest records which ran |
| OQ10 | **The synthetic tasks** (D13) | 5 ADB-style dataset-build tasks at three difficulty levels: find NAIP imagery for a county; list the open datasets covering an area of interest; build a list of candidate solar-farm sites (with USPVDB as the output answer key); find places that look like a given one, using embeddings; and one deliberately ambiguous task that should trigger errors. **Superseded by D52, D53, D69:** four task cards (synthetic keyed world, Nepal flagship, Virginia keyed, India stub). Keyed cards are the calibration and statistics set; synthetic only for method tests. Planted policies take over the ambiguous task's error-triggering role |
| OQ11 | **Exposing every parameter** (D11) | One run/eval spec schema (a Pydantic model, written as YAML/JSON), served by FastAPI with OpenAPI, so a future UI or the CLI reads every option from that schema. **Refined by ID §2:** the spec is `RunConfig`, `EvalSpec` and `TrustConfig` (Pydantic, exported by `treehouse schema`); the CLI exposes it first, FastAPI in W12 |
| OQ12 | **What the output metric is per task, and how it's scored** (D16). D9 said output *quality* doesn't matter, which argues against an LLM quality judge | Deterministic, task-specific checks against its reference (no LLM judge for output): e.g. precision/recall of returned sites vs. USPVDB, or whether the returned dataset IDs are the correct ones for the area. Reported as its own metric next to the workflow scores, never blended into them. **Superseded by D43, D45, D46:** output truth sources are answer keys **plus a blind sampled verifier** (DD1). Where keyed, the output grade stays deterministic (KEYED). Where unkeyed, there is no output grade; the trust passport gives a tiered estimate. The verifier is a separately reported, calibrated signal, never the grade. Output grade, process scores and trust are three separate numbers |
| OQ13 | **Team roles** (D14) | Parked by the team |
| OQ14 | **What does "we have it working" cover?** (round 3) Harness? Tracing? Task generator? The sandbox account? Where is it? | List what already runs, and where, so 06's dependency statuses can be updated. **Superseded by D67:** what runs in the AWS account is recorded by the K1 capability probe (`aws-capabilities.json`); build state is tracked in HANDOFF.md and TODO.md |
| OQ15 | **What "tooling" means in "compare harnesses, agents and tooling"** (D3) | MCP tool sets (which servers the agent can use). Tracer and evaluator swaps are covered separately by D2. **Refined by D68:** tooling comparisons in the MVP are with/without `clay_search` |
